## Project ownership

- `packages/db` owns D1 migrations and canonical D1 CLI scripts.
- `apps/web` and `apps/admin-api` bind the same logical D1 database as `DB`.
- Keep D1 config blocks synchronized across:
  - `packages/db/wrangler.jsonc`
  - `apps/web/wrangler.jsonc`
  - `apps/admin-api/wrangler.jsonc`
- `database_id` is currently a placeholder in checked-in configs. Do not run remote D1 commands until a real remote DB is intentionally provisioned and the ID is replaced everywhere.

## Local vs remote

- Local D1 and remote D1 are separate data stores.
- Use repo scripts for local work:
  - `pnpm --filter db db:migrations:apply:local`
  - `pnpm --filter db db:migrations:list:local`
  - `pnpm --filter db db:execute:local -- --command "select ..."`
- The repo shares local D1 state through `.wrangler-persist/`:
  - `packages/db` scripts pass `--persist-to ../../.wrangler-persist`.
  - `apps/web/vite.config.ts` sets Cloudflare Vite plugin `persistState` to the same location.
- Omitting `--local` on D1 commands targets remote data. Treat that as destructive unless explicitly requested and verified.

## Application query patterns

- Use prepared statements: `db.prepare(sql).bind(...values)`.
- Supported parameter styles include anonymous `?` and ordered `?NNN`; do not rely on named parameters unless current docs say they are supported.
- Use `.first<T>()` for one row and add `LIMIT 1` manually for performance.
- Use `.all<T>()` for result sets and read `.results`.
- Use `.run()` for inserts/updates/deletes where row data is not needed.
- Avoid `exec()` for application code; reserve it for trusted maintenance/migration SQL.
- In this repo, wrap D1 behind an Effect `Database` service rather than importing `env.DB` in domain code.

## Transactions and concurrency

- D1 `batch()` sends prepared statements in one call and runs them sequentially as a transaction; a failing statement aborts/rolls back the batch.
- This repo's admin sync uses `batch()` for optimistic concurrency with an in-batch guard trap. If changing that logic, read `apps/admin-api/src/effect/sync-guard.ts` and its tests first.
- D1 exposes SQLite-style error strings rather than typed constraint errors. If code message-sniffs errors, test exact local/workerd messages.
- Chunk large writes; do not build unbounded batches.

## Sessions and consistency

- D1 sessions (`withSession`) provide sequential consistency across queries and read-replica behavior.
- Use `first-primary` when the first query must read latest primary data; use bookmarks for cross-session consistency when needed.
- If code depends on read-after-write consistency across requests, confirm D1 session/bookmark behavior in current docs and test production-like behavior.

## Limits and design pressure

Design around D1 constraints:

- Bound parameter limit per query.
- SQL statement size limit.
- Query/batch duration limit.
- Row/string/blob size limits.
- Single D1 database throughput is not equivalent to a horizontally scalable PostgreSQL cluster.

Prefer bounded jobs, idempotent background work, and explicit chunking.
