Plan: Pivot Nusend to Cloudflare Workers + D1

Summary

Aggressively migrate Nusend from the current Bun/VPS/local-SQLite/Better-Auth direction to a clean Cloudflare-first foundation, as if Cloudflare Workers and D1 were the target from day one.

This migration is not the full product implementation. It should establish the new architecture and migrate the existing working foundation:

  • API-only Cloudflare Worker with Hono.
  • D1 as durable source of truth.
  • API-key-only authentication.
  • Durable Object dispatcher scaffolding for background work.
  • D1 job queue primitives ported to async D1.
  • Existing direct-recipient transactional POST /api/mailings migrated to D1.
  • List/campaign expansion architecture prepared with expand_mailing, while marketing creation remains blocked until unsubscribe support exists.
  • Public route contracts for unsubscribe and SES/SNS webhook.
  • PROJECT.md rewritten to the new Cloudflare-first vision.

No SES sending, real unsubscribe token handling, SNS signature verification, template API, placeholder rendering, R2 assets, dashboard, or CLI should be completed in this migration.

Confirmed Decisions

  • Cloudflare-first, not VPS/Bun.
  • No Bun runtime in v1.
  • API-only v1; no admin web UI.
  • CLI is future work and should be a thin HTTP wrapper only.
  • No orgs, workspaces, teams, sessions, Google OAuth, or Better Auth.
  • Single deployment = single tenant.
  • Multiple named API keys may exist, but no scopes/roles for v1.
  • API keys should use Authorization: Bearer nusend_... as the primary header.
  • Public unauthenticated route families are allowed for:
    • unsubscribe
    • SES/SNS webhook
    • health checks
  • Durable Objects are acceptable; Workers Paid plan is acceptable.
  • Cron cadence target: every 5 minutes (*/5 * * * *).
  • Cron is watchdog/janitor, not the primary sender loop.
  • Use one downstream sending pipeline based on deliveries + send_delivery jobs.
  • Direct transactional/small-recipient sends materialize deliveries immediately.
  • List/campaign sends use background expand_mailing to snapshot list recipients into deliveries and send_delivery jobs.
  • No Cloudflare Queues for v1. D1 jobs remain the source of truth; one Dispatcher Durable Object will eventually enforce global SES rate.
  • Drop the current unused templates table from the fresh schema. Document future templates as copy-on-create convenience over immutable mailings.
  • Delete the old untracked VPS/Bun SES worker plan files.

Research and Architecture Findings

Cloudflare Workers and D1

  • Workers use module exports such as export default { fetch, scheduled }.
  • D1 is accessed through environment bindings such as env.DB.
  • D1 statements are async: prepare(...).bind(...).run()/first()/all()/raw().
  • D1 supports anonymous and ordered positional params (?, ?NNN), not the current named params ($id, $now).
  • env.DB.batch([...]) executes statements sequentially as a transaction and rolls back on failure.
  • D1 otherwise operates in auto-commit mode; no interactive transaction callback like Bun SQLite.
  • D1 limits that shape the design:
    • 100 bound params per query.
    • 100 KB SQL statement length.
    • 2 MB max string/BLOB/row size.
    • 30s max SQL query duration.
    • 1,000 D1 queries per Worker invocation on paid / 50 on free.
  • D1 is single-threaded per database and queues concurrent work; too much concurrent work can return overload errors.
  • D1 migrations are Wrangler-managed forward SQL files in migrations/, tracked by d1_migrations.

Durable Objects and alarms

  • Durable Object alarms are official Cloudflare functionality.
  • A Durable Object can call ctx.storage.setAlarm(timestamp) to have Cloudflare wake it later via alarm().
  • Each Durable Object can have one alarm scheduled at a time.
  • Alarm execution is at least once and automatically retried if alarm() throws.
  • Only one alarm() invocation runs at a time per Durable Object instance.
  • A Durable Object is not a permanent process; it should process bounded slices, persist durable state in D1, then self-schedule another alarm if work remains.

SES sending rate implications

  • SES send rate is account/region-global, e.g. around 14/sec for some accounts but lower in sandbox.
  • The hard problem is global SES rate limiting, not just queueing.
  • Cloudflare Queues can deliver high throughput but do not provide the single global serialization point needed for SES rate limiting.
  • A single global Dispatcher Durable Object is the right primitive for the eventual SES token bucket / rate limiter.
  • Cron every 5 minutes should be a watchdog that restarts/pokes the dispatcher if needed, not the core send loop.

Templates/content model

  • mailings.subject/html/text plus deliveries.vars_json already represent a template instantiation.
  • Stored named templates are future convenience for reuse, not needed for the foundation.
  • Mailings must remain immutable snapshots; if templates are added later, template content is copied into mailings at creation time.
  • Future placeholder contract to document now:
    • syntax: {{ path.to.value }}
    • values resolved from deliveries.vars_json
    • HTML escaped by default
    • no loops, conditionals, or expressions in v1
    • missing variable fails the delivery terminally
    • Markdown source is never stored in Nusend; mdtoemail remains external

Jobs

Add flexible job support:

CREATE TABLE jobs (
  id TEXT PRIMARY KEY,
  kind TEXT NOT NULL,
  state TEXT NOT NULL,
  priority INTEGER NOT NULL DEFAULT 0,
  payload_json TEXT,
  run_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  attempts INTEGER NOT NULL DEFAULT 0 CHECK (attempts >= 0),
  max_attempts INTEGER NOT NULL DEFAULT 10 CHECK (max_attempts > 0),
  locked_by TEXT,
  locked_until TEXT,
  ref_id TEXT NOT NULL,
  last_error TEXT,
  created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
  updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
);

CREATE INDEX jobs_state_priority_run_at_idx ON jobs (state, priority DESC, run_at);
CREATE INDEX jobs_locked_until_idx ON jobs (locked_until);
CREATE INDEX jobs_kind_ref_id_idx ON jobs (kind, ref_id);

Rationale:

  • payload_json supports expansion cursors and future job parameters.
  • priority prevents large campaigns from blocking transactional send jobs later.
  • Do not use a CHECK on jobs.kind; future job kinds such as expand_mailing, send_delivery, process_ses_event, finalize_mailing should not require table rebuilds.
  • Validate job kinds/states in TypeScript.

Enum CHECK constraints

Avoid SQL CHECK constraints for evolvable workflow states/kinds:

  • jobs.kind
  • jobs.state
  • mailings.state
  • deliveries.status

Keep stable structural checks where useful:

  • mailings.purpose IN ('transactional', 'marketing')
  • suppressions scope/list consistency
  • numeric attempts checks

Rationale: SQLite/D1 cannot easily alter existing CHECK constraints without table rebuilds.

Auth Design

Implement simple API-key auth in src/auth/api-keys.ts.

Behavior:

  • API callers send Authorization: Bearer nusend_....
  • Middleware hashes the provided key with SHA-256.
  • Lookup api_keys.key_hash.
  • Reject missing, invalid, or revoked keys with 401.
  • Set a minimal principal such as { kind: 'api_key', apiKeyId } if needed.

Use SHA-256, not bcrypt:

  • Keys are high-entropy server-generated random secrets.
  • Slow password hashing protects low-entropy human passwords, not 256-bit random tokens.
  • SHA-256 avoids unnecessary Worker CPU cost.

Add scripts/create-api-key.ts:

  • generates a high-entropy key with prefix nusend_
  • computes hash
  • prints plaintext key once
  • prints a wrangler d1 execute command or SQL insert for local/remote use
  • does not add an admin endpoint

Mailings and Pipeline Design

Direct-recipient path

For transactional/small direct sends:

POST /api/mailings { recipients: [...] }
  -> validate max recipients
  -> create mailing
  -> resolve optional contact ids
  -> apply suppression filter
  -> create deliveries
  -> create send_delivery jobs
  -> poke Dispatcher DO
  -> return 201 with counts

Recommended direct-recipient cap: 100.

Rationale:

  • User intent: transactional emails go to single users or small numbers of recipients.
  • If callers need thousands of recipients, they should use contacts/lists/campaign flow.
  • The technical limit can be raised later without architecture changes.

Preserve existing direct-recipient error semantics:

  • malformed JSON: 400 invalid_request
  • invalid payload: 400 invalid_request
  • empty recipients: 400 invalid_request
  • all recipients suppressed / no sendable recipients: 422 empty_recipient_set

List/campaign path

For list-based mailings, the eventual flow is:

POST /api/mailings { listId: "..." }
  -> create mailing
  -> create expand_mailing job
  -> poke Dispatcher DO
  -> return 202-style response with mailing id and expansion state

expand_mailing means:

resolve list audience -> snapshot recipients -> apply suppressions -> create deliveries -> create send_delivery jobs

Expansion must be chunked, resumable, and idempotent:

  • Read list members by cursor.
  • Use jobs.payload_json for cursor state, e.g. { "afterContactId": "..." }.
  • Insert deliveries/jobs in D1 batches respecting the 100-bound-param limit.
  • Chunk’s delivery inserts, send_delivery job inserts, and cursor advancement / next expansion job insert must happen in one env.DB.batch().
  • Unique deliveries(mailing_id, email) is the final defense against duplicate expansion.
  • Queue the next expand_mailing job if more recipients remain.
  • Do not send; only create send_delivery jobs.

Marketing guard

Because unsubscribe support is not implemented yet, reject marketing mailing creation for now:

{
  "error": {
    "code": "marketing_unsubscribe_not_available",
    "message": "Marketing sending is disabled until Nusend has unsubscribe support."
  }
}

Implication for this migration:

  • Direct transactional sends are fully usable.
  • List/campaign API is architecturally prepared but marketing list campaigns remain blocked until unsubscribe support exists.
  • expand_mailing should still be implemented and tested directly with seeded data/jobs so the Dispatcher pipeline is proven without enabling marketing sends.

This guard should be removed only when real unsubscribe support exists.

Mailing state transitions for this migration

Define and test minimal transitions:

  • Direct-recipient transactional mailing starts as scheduled and remains scheduled while send_delivery jobs are queued because SES sender is not implemented.
  • List-based mailing created internally for expansion starts as scheduled.
  • When expansion completes, the mailing may move to sending or remain scheduled until sender exists; choose one in implementation and document it in tests. Recommended for this migration: keep it scheduled until an actual sender starts processing deliveries, to avoid implying sends are in progress.
  • Future sender moves mailings to sending and eventually completed.

Dispatcher Durable Object

Add real structural Dispatcher DO code now, but no SES sender.

Responsibilities in this migration

  • Expose a poke() RPC method to schedule an alarm soon if registered-kind work exists.
  • alarm() processes registered job kinds.
  • Registered initially: expand_mailing.
  • Not registered yet: send_delivery.
  • send_delivery jobs remain queued and untouched.
  • Re-arm alarm if registered-kind work remains.
  • Stop if no registered-kind work remains.

Use modern Durable Object RPC-style methods where practical instead of inventing a fetch sub-router inside the DO.

Processor registry

src/dispatch/processors.ts:

export const processors = {
  expand_mailing: createExpandMailingProcessor(...),
};

The dispatcher must always claim with the registered kind list.

Important safety rule:

  • If processor registry is empty, claim nothing.
  • Never claim send_delivery until a real sender exists.
  • Never mark send_delivery succeeded without sending.

queue/runner.ts role

Repurpose queue/runner.ts as pure reusable queue tick logic called by the Dispatcher:

claim registered jobs -> process -> complete/fail -> summarize result

This keeps the Durable Object class thin and makes the claim/process/complete behavior easier to test outside the DO wrapper.

Scheduled watchdog behavior

The Worker scheduled() handler should do only:

  1. release expired leases
  2. if queued jobs of registered kinds exist, poke the Dispatcher DO

It should not process jobs directly.

Future SES sender phase

Later, register send_delivery processor:

  • global SES token bucket inside Dispatcher DO
  • max rate from config / optional GetSendQuota
  • send via SES v2 signed HTTPS (aws4fetch)
  • write send_attempts
  • update deliveries
  • retry/dead-letter via D1 queue

Risks and Mitigations

Expansion idempotency

Risk: Durable Object alarms are at least once. If expansion retries a chunk after partial work, duplicate deliveries/jobs could be created.

Mitigation:

  • chunk delivery inserts, send job inserts, and cursor advancement must be one D1 batch()
  • add unique index on (mailing_id, email)
  • write explicit idempotency tests

D1 limits during expansion

Risk: D1 100 bound params and per-invocation query limits.

Mitigation:

  • chunk recipient reads and multi-row inserts
  • keep direct recipients[] cap at 100
  • use list expansion for large audiences
  • bounded Dispatcher processing slices

Transactional latency during campaigns

Risk: campaign work blocks password resets.

Mitigation:

  • direct transactional materialization
  • jobs.priority
  • future sender claims high-priority jobs first

Fake processing of send jobs

Risk: queued emails marked succeeded without SES.

Mitigation:

  • send_delivery not registered in dispatcher registry until real sender exists
  • explicit tests for this

Marketing without unsubscribe

Risk: compliance failure.

Mitigation:

  • reject marketing creation until unsubscribe route is implemented

Durable Object alarm at-least-once behavior

Risk: duplicated processing after retry.

Mitigation:
